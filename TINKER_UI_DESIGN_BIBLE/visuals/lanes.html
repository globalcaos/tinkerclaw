Command lanes

Why one stuck tab cannot freeze the others — and why the fix was a second, nested lane.

The nesting (this is the part people get backwards)

enqueueSession(session:<sessionKey>)  — concurrency 1, always
→ enqueueGlobal(sessions / main / cron / subagent) — concurrency from config

run.ts:321-323 is literally enqueueSession(() => enqueueGlobal(work)). The session lane is the outer one, and a run holds its session slot while it waits for a global slot. That is what makes per-tab ordering strict (one turn per session, ever) without letting any single tab consume more than one unit of global capacity.

Live values on this machine at the time of writing: main 4, sessions 8 (unset → default), subagent 8, cron 6.

The incident this shape exists to prevent

Before eba0911c7b (2026-07-24) embedded session runs defaulted to the shared main lane. On 2026-07-22 a hung compaction wedged a run there, the lane filled, and every Tinker tab froze — including tabs doing nothing wrong. Splitting tab runs onto sessions means a wedge consumes tab capacity only; system work on main keeps its own four slots. Press Wedge above until sessions is full, then press System work: it still runs.
