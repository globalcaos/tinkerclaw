## Failure modes

### M1. tinker-bridge SIGTERM (LLM idle watchdog)

- **diagnose_with:** `debug.session.config({provider:"claude-code"})` → assert `resolvedRequestTimeoutMs=600000`. `gateway.stuckSessions({thresholdMs:120000})` → if a session is past the old 120s threshold but `resolvedRequestTimeoutMs=600000`, the watchdog is correctly relaxed; otherwise the overlay broke. Journal grep `[idle-timeout-diag]` confirms per-turn resolution.
- **Origin:** `streamWithIdleTimeout` in `src/agents/embedded-agent-runner/run/llm-idle-timeout.ts`. Idle timer racing `streamIterator.next()`. tinker-bridge intentionally does NOT emit `stream` events during tool work (see `tool-loop.md`), so heavy turns can starve the timer.
- **Propagation:** idle timeout rejects → `idleTimeoutTrigger(error)` → `abortRun(true, error)` aborts `runAbortController` → tinker-bridge worker receives signal → `worker.kill("SIGTERM")` → claude-cli exits → `assistant-failover.ts` classifies as `surface_error reason=timeout`.
- **Envelope:** category `timeout` (icon ⏱️) or `lane_busy` if classified that way. Text: `"🤖 ⚠️ Something went wrong while processing your request."`
- **Surface:**
  - WhatsApp: envelope delivered as chunked text via `deliverWebReply`. User sees the chip.
  - Tinker UI: pre-2026-05-10 → spinner stuck on `sending...` (lifecycle event dropped). Post-fix → backstop `broadcastChatFinal` fires; chip renders, spinner clears.
- **Resolution:** ensure `timeoutSeconds` is correctly resolved (see config-shape.md M1 ↔ that file). Architectural fix LIVE 2026-05-11: tinker-bridge now emits an empty-delta heartbeat every 25s during a turn so the watchdog resets without re-executing tools. The 600s overlay is now belt-and-suspenders rather than load-bearing. See `tool-loop.md`.
- **Detection probe:** journal grep `[llm-idle-timeout]` lines, plus the `[idle-timeout-diag]` log shows the resolved timeout. Heavy turns hitting 138s/279s without `[idle-timeout-diag] idleTimeoutMs=600000` means the overlay path broke.

### M12. Schema-migration ordering bug (CREATE INDEX before ALTER TABLE)

- **diagnose_with:** `journalctl --user -u openclaw-gateway.service --since today --no-pager | grep -E 'SqliteError: no such column'`. Cross-check `openclaw gateway call plugin.boot.status --params '{"status":"error"}'` — a plugin with `failurePhase:"register"` and a SqliteError in its error trace is M12.

On any existing DB (where `<new_column>` doesn't exist yet because the migration hasn't run), `CREATE INDEX` throws `SqliteError: no such column`.
- **Propagation:** plugin registration crashes mid-schema. The loader silently re-registers several times after the initial failure — but those re-registrations land AFTER the HTTP server starts listening, so the RPC routing table never picks them up. Every `<plugin>.*` RPC call returns `unknown method`.
- **Surface:** the entire plugin disappears from the running gateway with no obvious symptom in the user-visible UI (just "RPC unknown" toasts when something tries to call it). The 2026-05-22 instance: `control-panel.*` calls all returned `unknown method` after a v3.5 boot on a v3.3 DB.
- **Resolution (2026-05-22, commit `e60c1f45c9`):** drop the offending `CREATE INDEX` from `schema.{sql,ts}` entirely; create it inside the migration that adds its column (`addAxisParentIdColumn` in `db.ts`, idempotent with `IF NOT EXISTS`). - **Rule:** indexes that depend on newly-added columns ALWAYS live in the migration that adds the column, never in `schema.{sql,ts}`. Schema files describe the **final state**; migrations describe the **transition**. Mixing them produces an unrecoverable boot crash on any DB that wasn't created in the post-migration era.

### M14. Browser-relay CDP assert crashes the WHOLE gateway (subsystem fault isolation)

- **diagnose_with:** `journalctl --user -u openclaw-gateway.service --since today --no-pager | grep -nE 'Unhandled promise rejection|Assertion error|crConnection|CRSession._onMessage|stability bundle'`. The signature is an `Error: Assertion error` whose stack runs through `playwright-core/.../server/chromium/crConnection.js` (`CRSession._onMessage` → `assert`), immediately preceded by a burst of `[browser/extension-relay] [relay-cdp]` lines re-attaching CDP to a shared tab `tc-tab-N`. **The tell is a duplicate `Page.enable` on the same `tc-tab-N` within a few ms** (two `ext id=` for one sessionId) — a session-lifecycle race. systemd shows `ActiveState=failed`, `MainPID=0`; the stability bundle reason is `unhandled_rejection`. - **Origin:** the browser/extension-relay re-attaches CDP to a shared tab and issues two `Page.enable` for the same `tc-tab-N` (concurrent attach, no dedupe). The throw surfaces as an unhandled promise rejection.
- **Propagation (the real fault line):** PRE-FIX, the global handler in `src/infra/unhandled-rejections.ts` treated **any** unhandled rejection it did not specifically recognize as FATAL → `process.exit(1)`. So one subsystem's async hiccup (the browser relay) killed the entire gateway — chat, crons, channels, memory — and `Restart=no` (the `no-restart.conf` drop-in) kept it down until a manual restart. This is the same class as the 2026-05-28 whatsmeow leak (`isBenignGoProcessExit`): a subsystem async throw leaking into the global default-exit arm.
- **Surface:** gateway suddenly DOWN/frozen, Tinker UI shows no activity, Jarvis unresponsive on every channel — with NO code/deploy cause. Looks like a frontend or worker-pool failure; is actually a backend crash triggered by a background browser-automation burst.
- **Resolution (2026-06-09) — FOUNDATION, subsystem fault isolation:** the global `unhandledRejection` default arm is **inverted** from "exit" to "contain". `classifyUnhandledRejection()` now returns `contain` for any rejection that is not in the curated fatal class (`fatal` = OOM/worker-init, `config` = misconfig) or a known-survivable class (`abort`, `benign-go-exit`, `transient` network/SQLite).   - `phase=queued`, `preflight_compacting` or `memory_flushing`: the gateway accepted the turn and has NOT handed it to its run. A pre-model wait (the 2026-09-23 recurrence below: prompts waiting 5–17 min between dispatch and `llm_input`), not a hung model call.
  - `phase=running`: the reply operation handed the turn to its run (agent-runner.ts sets the phase just before `runAgentTurnWithFallback`). That is NOT proof the model was reached. With `sessionId=unknown` the embedded run has not registered yet, so the turn is still in the lanes or the attempt prelude (prompt-queue.md §4, holder E). With a sessionId the run is registered, and the question becomes "hung, or the bridge false positive above".
  - `phase=aborted`: a stop or a restart aborted the operation, which stays registered until its run lets go (reply-run-registry.ts: an abort clears the registration at once only from `queued`). `completed` and `failed` clear the registration in the same call (`complete()`, `fail()`), so the line should never show them.
  - `phase=none`: the probe ran and found no reply operation under that key. A real state, spelled apart from "not wired": dispatch marked the session processing (holder A) before any operation exists, or the turn lives where the key cannot reach it (a native command's or a bound conversation's retarget, a channel plugin's own key normaliser, a state that carries only a sessionId).
  - `phase=unknown`: the probe threw. The seam logs it at debug and swallows it, because it runs inside the heartbeat's timer.
  - No `phase=` at all: the heartbeat was started without a probe (a pre-G6 build, or a process whose first starter passes none: the heartbeat is a singleton, and gateway startup starts it through `startGatewayDiagnosticHeartbeat`, with the probe).
  - **Wiring.** The probe is `createGatewayReplyPhaseProbe` (src/gateway/server.impl.ts). It resolves the key through reply-registry-key.ts `findReplyOperation`: the RAW dispatch key as given, then the key `initSessionState` derives from it, and nothing else. It never tries the STORE key, because `resolveSessionStoreKey` folds spellings the registry keeps apart (with no `main` agent configured, a legacy `agent:main:<mainKey>` is stored as `agent:<default>:<mainKey>`), and a folded spelling would name ANOTHER dispatch's turn. The phase is in the log TEXT only: the `gw.session.stuck` bus event carries `reason`, never the phase (logging.md §4.1). The seam first landed with no caller (`905dba34d9d`: green tests, and production never printed the field) and was wired by `8d31a82b88c`, so the frontmatter `M10/M20 (G6)` verify pins the startup wiring, not only the seam.
- **Live instance:** 2026-09-14, seven tabs open: ≈60 MB/min of `readFileSync` + line-by-line `JSON.parse` of 3–7 MB transcripts on the main thread (one of them last written on 2026-09-07), RSS 5–6.5 GB all anonymous, GC helper threads busy, `ws handshake timeout` for new clients, the CLI's own `chat.history` call dying on its 10 s deadline.
- **Origin:** `readClaudeCliSessionMessages` re-read and re-parsed the whole transcript on every poll for every tab, idle or not.
- **Resolution (2026-09-14, `7c73977b74d`):** stat-keyed incremental cache — unchanged file = zero I/O; grown file = tail-only parse; anything else = full read; output byte-identical to a cold read (asserted by `cli-session-history.cache.test.ts`). Secondary: `debug.dumpUiSnapshot` acknowledges before its write lands (`ba8cb3d504f`).
- **Measured, not fixed (follow-ups):** five plugin activations per gateway start — each fork plugin's timers run ×5 (pulse-panel showed 5 `gh` polls/min for a single 60 s metric); an UNCOMMITTED pulse-panel `github-activity` poller with a broken GraphQL type (`$since: DateTime` vs `GitTimestamp`, 916 failed `gh` spawns that day) — absent from `dist` on any clean-SHA deploy; `sessions.json` 14 MB of which 10 MB is `skillsSnapshot` duplicated into 109 entries (rewritten rarely, so not on this path).
- **Don't regress:** nothing that scales with transcript size goes on the `chat.history` poll path unless it is incremental or cached by `(ino, size, mtime)`. Verify: M20 in the frontmatter.
- **Bug history:** stalls visible in the journal every day of the week of 2026-09-08 (318 liveness warnings on 09-10); root-caused and fixed 2026-09-14.
- **Recurrence in the SIBLING path, fixed 2026-09-23 (`feat/chat-history-incremental`, plan tasks 2–5).** The 2026-09-14 fix above covers only the claude-cli IMPORT path (`cli-session-history.claude.ts`). The session's OWN transcript path — `readSessionMessages` / `readSessionMessagesWithCursor` in `src/gateway/session-utils.fs.ts` — still did `readFileSync` + `JSON.parse` of the WHOLE transcript on every `chat.history` poll, then handed it to pi's `SessionManager.open`, which could rewrite the file. Measured 2026-09-23 12:00: ELU=1 from one minute after boot, `chat.history` ~22 calls/min against 10–24 MB open-tab transcripts, `sessions.json.lock` held 40–53 s, prompts waiting 5–17 min between dispatch and `llm_input`. Same fault shape as the paragraph above (re-read the whole file every poll), different code path. **Fix:** `src/gateway/transcript-index.ts` — a per-file `TranscriptIndex` that tail-parses only the bytes appended since its last refresh (keyed on `(ino, size, mtime)` exactly as this M20 rule already required, PLUS two rewrite-detection probes — a same-length header/id swap defeats a naive tail-only stat check, see the module's own R2 tests) and rebuilds fully only on an actual rewrite (repair, compaction, branch switch, pi migration). `readSessionMessagesWithCursor` serves the tree-transcript path from the index when it is safely equivalent to pi's own reader (39 parity cases against pi's `SessionManager`, real-data census: 47/47 live session transcripts index-eligible) and falls back to the legacy full read otherwise. `epoch = ${processNonce}:${ino}:${generation}:${branchRootId}` — unique per process AND per rebuild, so a registry eviction or a restart can never hand a client a REUSED epoch for different content (ruling R19). The registry that holds live indexes is bounded by BOTH count (16) and total indexed bytes (512 MiB, `OPENCLAW_TRANSCRIPT_INDEX_MAX_BYTES` env override — unset/NaN/≤0/Infinity fall back to the default, `resolveTranscriptIndexMaxBytes`, raised from 192 MiB FORK 2026-09-23), so a burst of huge transcripts cannot grow it unbounded; an eviction of an index refreshed under 60 s ago now warns (subsystem `gateway/transcript-index`, basename only, rate-limited to ≤1/min with the count of such evictions since the last warning — thrash detection, FORK 2026-09-23, ruling R20). See flows.md F8 for the cursor protocol this enabled (`afterSeq`/`beforeSeq`/`epoch`) and tinker-ui.md §5.8W for the client-side window this feeds.
- **Don't regress (extended 2026-09-23):** the `(ino, size, mtime)` rule above is necessary but NOT sufficient for an in-place rewrite that keeps the same byte length — a stat-only check can miss a same-length content swap. Any new incremental transcript cache needs a rewrite-detection probe stronger than a size check (`transcript-index.ts`'s two-probe design, or equivalent), and its epoch/generation counter must be unique across a registry eviction and a process restart, not just within one live instance (ruling R19).

### M21. Session-store save/read paths pay an unconditional whole-store `structuredClone` under the write lock

- **diagnose_with:** the same `session-write-lock … held for` warnings and 5–17 min dispatch→`llm_input` gaps as M20's 2026-09-23 recurrence above; `diagnostic.cpuProfile` shows `structuredClone` inside `readSessionStoreCache`/`writeSessionStoreCache`, reached from `buildSessionEventSnapshot`, `chat.history`'s `loadSessionEntry`, and task-registry maintenance — measured 2026-09-23 14:40 (post-restart) at ~20–23% of main-thread CPU, alongside memory-layout.md's total-recall FTS finding (~35–42%).
- **Origin:** two separate costs, both paid even when only ONE entry of a 198-entry / 3.7 MB live store is touched. (1) Every SAVE ran `externalizeSessionStoreSkillsSnapshots`, which re-`JSON.stringify` + sha256-hashed every entry's `resolvedSkills`/prompt text on EVERY save regardless of whether the content had changed — measured ~65–69 ms/save on the live store (198 entries, only 17 distinct `resolvedSkills` arrays). (2) Every save's cache write, and every read of `loadSessionStore(path)[key]` / `loadSessionEntry` / `resolveGatewaySessionStoreTarget`, ran a full `structuredClone(store)` — measured ~32 ms per clone on the save side, ~58–64 ms per single-key READ — even though the caller only ever touched one entry.
- **Resolution (2026-09-23, `feat/chat-history-incremental`, plan tasks 11 and 13):**
  - **Hashing memo, content-keyed.** `skills-snapshot-store.ts` memoizes by CONTENT (`Map<JSON.stringify(resolvedSkills), ref>` / `Map<promptText, ref>`, 64-entry LRU each, plus a per-save identity dedupe so each distinct array is stringified once per save, not once per entry) — not by object identity. A WeakMap-by-identity design was tried and CONTROL-proven to serve a STALE ref after an in-place array mutation (nothing writes in place today, but a future writer would silently corrupt disk). Externalize: 68.7 ms → 4.2–5.0 ms (reloaded store) / 6.8–7.9 ms (a freshly `structuredClone`d store — still content-recognised, which identity keying cannot do).
  - **Save-path clone, per-entry-point audit.** `store.ts`/`store-cache.ts` decide, per CALLER, whether anything a save returns can still be reached and MUTATED afterward. `updateSessionStoreEntry`/`updateLastRoute`/`recordSessionMetaFromInbound` (each touches exactly one entry; the audit found every caller of their returned entry DOES mutate it later, e.g. `agent-runner.ts` writing `activeSessionEntry.updatedAt` in place) now ADOPT the just-saved store into the cache directly and deep-copy only that ONE entry — zero whole-store clones, was ~32 ms. The generic `updateSessionStore` (arbitrary mutator) and the plugin-SDK-exported `saveSessionStore` KEEP the clone: the audit found 79+ non-test call sites across auto-reply, gateway and channel extensions that store a caller-held live entry back into the store, return the in-store entry to a caller who mutates it, or capture it via closure — none safe to expose without a copy — and the plugin surface (third-party `saveSessionStore` callers) is unauditable at all.
  - **Read-path clone, routed accessors.** New `loadSessionStoreEntry(path, key)` (returns a `structuredClone` of ONE entry, or `undefined`) and `hasSessionStoreEntry(path, key, {ignoreCase})` (returns a boolean, ZERO clones) in `src/config/sessions/store-load.ts`, routed into the hot gateway paths that only ever needed one entry or a membership check: `resolveGatewaySessionStoreTarget`/`resolveGatewaySessionStoreLookup` (the target-lookup key scan behind `chat.history`, `loadGatewaySessionRow`, every `sessions.changed` row — this was the HIDDEN clone behind `chat.history`, not the lazy `store` getter that looked more likely; it borrows the store read-only, since it only returns paths/keys), `hasBackingSession` (task maintenance), `readSessionUpdatedAt` (every inbound channel message), and two verbose-level gates (per tool/progress event). Measured on the live store: `loadSessionStore(p)[key]` 58–62 ms / 220 clones per 200 calls → `loadSessionStoreEntry` 0.5–0.9 ms / 0 clones; `resolveGatewaySessionStoreTarget` 58–65 ms → 0.15–0.19 ms.
  - **End to end (median, live store copy):** `updateSessionStoreEntry` 161.0 ms → 60.5 ms; `updateLastRoute` 183.4 ms → 77.3 ms; `recordSessionMetaFromInbound` 163.7 ms → 57.3 ms. The generic `updateSessionStore`/`saveSessionStore` paths stay near their baseline (~85–100 ms) BY DESIGN — the audit forbids adopting them there.
- **Don't regress:** a save or read path may skip the whole-store clone ONLY after an explicit per-call-site audit proves nothing the call returns is both (a) reachable by the caller after the call and (b) ever mutated in place by that caller. Closures, plugin-SDK exports, and "store the returned entry then patch it later" call sites (the majority of hits in the audit) all fail that test and must keep the clone. Do not generalize "single-entry save/read → no clone" to the generic `updateSessionStore`/`saveSessionStore`, or to any plugin-reachable path, without redoing the audit for that specific call shape.
- **Don't regress, the row-builder corollary (2026-09-24/25).** `buildGatewaySessionRow` runs per row, per `sessions.list`, per open tab, and wave-0924 gave it two new fields. Both read in-memory state ONLY: no session-store read, no database read. A7's compaction-ledger figures (`compactions`, `evictions`, `droppedTokens`, `lastCompactionAt`, beside the entry's own `compactionCount`; context-window-panel.md §6.1 A4 and A7) come from `readCompactionLedger` (src/infra/compaction-ledger.ts), which answers from memory and seeds a session's earlier-process history lazily on the events writer's worker, one batched request per microtask, never on the main thread (logging.md L3). G5's `pendingPrompts` (prompt-queue.md §6.3) comes from `deriveSessionPendingPrompts`, which reads the reply-run registry, the follow-up queue, the steered-prompt list, the run set and holder C's accepted mark. Both are ABSENT, not zero, when they have nothing to state (an unseeded session; nothing pending). Each is pinned by a counting spy with a positive control that proves the spy is wired: session-utils.pending-prompts.test.ts ('deriving it adds no session-store read') and session-utils.compaction-ledger.test.ts ('no store read, no database load'). A NEW row field inherits the rule: a field that needs a store or database read does not belong on this path, because this path's multiplier is what made M20 and M21 user-visible. Verify: `M21 (row builder)` in the frontmatter.
- **Not fixed here (named follow-ups, not defects):** the generic `updateSessionStore`/`saveSessionStore` still pay the ~30 ms whole-store clone (options on record: migrate hot call sites to the single-entry accessor shape; build the cache from the JSON already produced instead of a second `structuredClone`; or drop the object cache on a generic save and let the next reader cold-load); `updateLastRoute`'s own `clone:true` LOAD (not its save) still clones; the cold-load cache fill in `store-load.ts` still clones on a miss, exactly as before this fix.
- **Bug history:** root cause profiled 2026-09-23 14:40 (post-restart `diagnostic.cpuProfile`, taken alongside the total-recall FTS finding above); fixed the same day.

### M22. A pending turn survives `sessions.delete` / `sessions.reset` (RESOLVED 2026-09-24)

- **diagnose_with:** a turn that runs on, or an indicator that stays lit, AFTER its session was deleted or reset: `sessions.list` still reports `run.live` for the old key, the Tinker UI never receives a terminal for the prompt's runId, and a backlogged prompt just disappears. On the typed path the gateway log names the leftovers: `typed reset: <n> backlogged prompt(s) of <key> dropped with no chat terminal` and `typed reset: a turn of <key> did not stop in time; resetting anyway`.
- **Origin:** before G1, delete and reset ended only a REGISTERED embedded run (prompt-queue.md §4, holder E). A turn still before the model kept its reply operation (holder D), its chat abort controller (C) and its run-set entry (B), and `clearSessionQueues` only COUNTED the backlog it dropped. A `/new` or `/reset` typed in chat never reached an RPC reset at all: `initSessionState` rotated the sessionId under the running turn and cleared its queues without a terminal.
- **Propagation:** the turn could run on against a soft-deleted session whose transcript was being archived; `run.live` stayed true until the silent 30-minute run-set sweep; every indicator of a dropped prompt waited for a terminal that never came (prompt-queue.md C10, C11). Found by the 2026-09-23 restart investigation (bug-log.md, "Investigated, NOT fixed"), which also showed that the `sessionId=unknown` turns it flagged were pre-model waits, not orphans (M10, M20).
- **Resolution (G1, `3b0ef8e7b5e`; typed path `ae8261ea05d`, `b5dbfc9d573`):** ONE terminator, `endSessionTurns` (src/gateway/session-reset-service.ts; prompt-queue.md §6.2). Its callers are `sessions.delete` and `sessions.reset`, the `agent` method's `/new` and `/reset`, the TUI and ACP resets, and a `/new` or `/reset` typed in chat, through `endTypedResetSessionTurns`, which spares the command's own run by `exceptRunIds`. Every abort fires before the first await. Each chat run and each backlogged prompt key gets exactly one `aborted` (PQ-6), chat.send's completion path stays silent for a run already aborted (D2), and `abortedLastRun` is never written, so a reset cannot hand the fresh session M10's false "aborted by the user" prefix.
- **Still open:** a stale-session rollover (idle or daily expiry, no command) clears the old backlog with no terminal; a reset with no chat-run state (TUI, ACP, or a typed reset arriving on a channel) ends the run but only counts its backlog (`unannouncedBacklog`); a gateway restart loses the in-memory follow-up queue. The Tinker UI derives such a prompt LOST, with Resend and Dismiss (lifecycles.md L-PROMPT, edge 2).
- **Don't regress:** a new path that deletes, resets or rotates a session calls `endSessionTurns`. It never goes through `chat.abort` (its requester authorization would newly fail a delete, and it stamps `abortedLastRun`), and it never clears one holder on its own. Verify: prompt-queue.md `G1 / PQ-6`, `G1 / D2` and `G1 / C11`, and lifecycles.md `L-PROMPT edges`.

## Faults that surface as silence

Every mode above surfaces as _something_ — a chip, a spinner, wrong text, a dead channel. This section is the class the propagation graph structurally cannot draw, because the edge that fails is the one that was never there: **the work does not happen, and the only thing that reaches a human is a status line saying it went fine.**

```mermaid
flowchart LR
  T["the trigger fires<br/>cron tick · RPC call · nightly run · search query"]
  W["the work"]
  A["THE ARTIFACT the work exists to produce<br/>a report file · a non-empty result set ·<br/>a response frame · a consolidated episode"]
  S["the wrapper's OWN bookkeeping<br/>status ok · a plausible duration · exit 0 · an empty list"]
  R["what every monitor actually read"]

  T --> W
  T --> S
  S --> R
  W -.->|"THE MISSING EDGE — nothing asserts this"| A
  A -.->|"the only thing that would have proved the work happened"| R
```

**Read the graph.** The status line reaches the reader on a path that never touches the artifact. Sever `work → artifact` and _nothing observable changes_. That is why this class survives for months while a loud failure is fixed in an afternoon.

The ingestion repair is entangled with session-key normalisation (UI chats read `agent:main:tinker:*` stores that nothing writes)                                                                                                                                                               |

**The unifying lesson, sharpened by the second four: not one of these eight produced an ERROR. Every one produced a PLAUSIBLE NON-ERROR** — a green status line, an empty result set, a healthy-looking no-op, a `warn` nobody reads. That is the defining property of the class, and it is sharper than "they all reported success", because rows 5–8 mostly reported nothing at all; they simply _returned_. What they share is that **every value they emitted is a value the HEALTHY system also emits**: `ok`. `[]`. "not eligible". "no nudge this cycle". Zero vectors in a table that is legitimately empty on a fresh install. A monitor diffing against the healthy shape finds no difference, by construction — which is why all eight were caught by a human reading a number, and none by a gate.

A green status line records that the _wrapper_ completed its own bookkeeping. It is not evidence that the work happened, and it is fully compatible with a dead code path — a green status, a plausible duration and exit 0 were all present in each of the first four rows. **The only evidence of work is the artifact the work was supposed to produce.** Assert on the artifact — and pick one whose ABSENCE is not also a healthy state.

Corollaries, each earned:

- **A fast, clean run is the tell, not the reassurance.** ~6 s with 15 output tokens, and ~10 ms with `status:"skipped" error:"disabled"`, are both what doing nothing looks like from outside. They are **two different receipts** — the 2026-07-25 wake-key instance and the 2026-08-03 disabled-cron instance — and must not be merged into one incident.
- **Duration is not evidence in either direction.** A main-session turn that gets the empty poll still burns 20–120 s reading ~50k tokens of context before answering. Two prior "fix confirmed" calls (98,715 ms and 117,448 ms) were both this same no-op.
- **"No data" must never render as PASS.** A monitor that reports health while observing nothing is another instance of this same bug; `cron-health-gate.log` logged "OK: all cron jobs healthy" every 3 minutes across a full week of silence — the watchdog checked that jobs ran, never that they produced anything.
- **Never let a `catch` degrade to an empty result without logging the throw first.** Best-effort return contracts are fine; silent ones are not.
- **A handler's `respond` must be DERIVED from the live registration signature**, never re-declared locally. Deriving turns an arity mistake into a compile error; re-declaring turns it into a hang that reads as a slow model.
- **A default that names a store, session or file must fail loudly when that name resolves to nothing.** "Nothing to do" and "the path is dead" are different states and must exit differently, or 83 dead nights read as 83 quiet ones.
- **One fix per fault, verified separately.** Row 1 had two independent faults producing one receipt; the first fix shipped, the symptom persisted, and the natural reading was "the fix didn't work" rather than "there is a second fault". A repro run on a build that provably contains fix (a) is what separated them. Row 5 repeated it inside a single day: the verify-after-CREATE in `bc16efe811c` was correct and UNREACHABLE, because the early return above it took the fast path on a lying `meta`. **Deploy, then re-measure the same number** — the second measurement is what found it.
- **`warn` is where you put something you have already decided not to act on.** 198 identical `memory sync failed` lines in three days, under a quarter-million backfill lines, are indistinguishable from no signal at all. A fault that disables a feature belongs on the **error** channel, and the feature belongs disabled and named — not retried forever at warn.
- **Never record a measurement you did not take.** `ensureVectorTable` wrote `this.vector.dims = dimensions` after a CREATE that is a NO-OP on a surviving table, and `meta.vectorDims` then carried the lie across every restart. Persisted state is a CLAIM; the schema is the truth. Read it back before you trust it, and again after you change it (`design-principles.md` #20).
- **A failure must not return the success TYPE.** A failed flow registration returned a record byte-identical to "not eligible"; an unclassified RPC returned a completed Overseer cycle with nothing in it. When the failure and the healthy decline share a shape, the fix is a distinguishable OUTCOME — a closed reason union, a health accessor — not a louder log line on the same shape. Same shape on the chat surface (2026-09-29): 349 failed turns came back after a reload as ordinary answers, because the failure lived in fields the renderer never read; the fix is a typed `outcome` on the row (`tinker-ui.md` §5.8AB), not an error word in the text.
- **Unclassified is not neutral.** A method missing from the scope table made the client ask for `[]` and the server demand admin: a default-deny that reads as "nothing to do". Any registry with a fallback needs an exhaustiveness test that FAILS on the unclassified set rather than counting it — the one in `src/gateway/method-scopes.test.ts` had been passing on 33 of them.
- **A diagnostic nobody polls is not a diagnostic.** If a refusal disables a feature, it goes where people already look — the journal — in the same commit that adds the refusal. An in-memory array behind an RPC is a place for detail, never the only copy.
- **A green suite can be structurally blind.** The flow-registry defect exists only on a database created before the migration; the fresh-install DDL never had the offending column, so 129 passing tests said nothing about any real machine. When a fault is schema-history-dependent, the fixture must be a MIGRATED one.

### What to run instead of trusting the status line

`scripts/post-deploy-smoke.mjs` was written for this class specifically, after these exact fixes. Its contract is the inverse of the failure — _every check prints what it SAW, not just a verdict_ — and blindness is a FAIL rather than a pass. `probes.md` owns the probe registry and the check table: go there for the call rather than inventing one. Neither is restated here. Three of the FIRST four shapes are covered by the smoke directly — a cron skipping itself into silence, the phantom `events/live.jsonl` store reappearing, and the instrument-liveness registry (written precisely to catch components registered but never run) shipping with no caller for its own report. Run it after every deploy.

**The 2026-08-04 four are NOT covered yet.** `S6`–`S9` are source assertions: they catch a REGRESSION of each fix, not a fresh recurrence on a live box. The live checks they still need are one query each — `chunks_vec_rowids` non-zero whenever `chunks` is non-zero; a `flow_runs` row newer than the last deploy; a non-empty scope set for every registered `fork.*` method; and a `conversation hook DROPPED` grep over the boot log. Those belong in the probe registry and the smoke runner, neither of which this optic owns — see `probes.md`.

A new failure of this class belongs in the tables above **and** gets a source-assertion `verify:` in this file's frontmatter that goes red when its guard is removed — eleven exist now, named `S1`–`S9` (with `S1b` and `S2b`). `S6`–`S9` are one-line pointers into [`scripts/bible/failures-silence-guards.mjs`](../scripts/bible/failures-silence-guards.mjs), per FOUNDATION.md's "Three different jobs, three different homes": the optic EXPLAINS, the script CHECKS. That script's `--self-test` proves each guard actually goes red when its token is removed, because **a guard that cannot fail is another instance of the very class this section is about.** Keep them OUT of the M-numbering: an M-row is indexed by origin and owes a `diagnose_with:` probe, and a fault whose defining property is that nothing observed its absence has no origin edge to hand such a probe.
