**The invariant this optic protects.** Every row in the events database has a name the catalog in §4 declared first, carries no free text, and was written off the gateway's main thread. A row that breaks any of the three is a defect in the writer, not a judgement call.

**Code, not prompt** (design-principles #22). What gets recorded must happen the same way on every turn, and there is a structural producer for every row, so the catalog is enforced in code: the writer rejects undeclared names and keys, and `scripts/bible/` checks the code catalog against §4. The one plastic part is which questions get asked — ad-hoc SQL from the CLI (§8) — and that stays a human or agent choice.

## 1. The problem, measured

1. **The journal is where most runtime facts land, and it is text.** A regex over a log line is not an interface: observability.md §7 records how `post-deploy-smoke.mjs` stopped parsing `[instrument-liveness]` after a format change while its own self-test stayed green.
2. **The text carries what must never be stored.** `extensions/tinkerclaw-prefrontal/recipe-matcher.ts:726` prints a prompt snippet. `[total-recall] pack refreshed`, `[chat-deliver]`, `[duprep-history]` and `stuck session` print raw session keys, and a channel session key can embed a phone number. `claude exit[…]` prints a stderr tail, which can echo prompt content. A database filled by scraping the journal would inherit every one of those.
3. **The retention is wrong for trends.** The rolling file log keeps 24 hours (`src/logging/logger.ts:59`, `MAX_LOG_AGE_MS`). journald's window is host configuration that does not travel with the state directory (FOUNDATION #9).
4. **The samples that exist are biased.** The 30 s diagnostic heartbeat (`startDiagnosticHeartbeat` in `src/logging/diagnostic.ts`, period `DIAGNOSTIC_HEARTBEAT_INTERVAL_MS`) emits `diagnostic.memory.sample` only when there was recent activity or open work (`shouldRecordMemorySample`, `:760-766`), so an idle gateway has no memory series — and the idle baseline is exactly where a leak shows. The liveness sampler throws away every healthy sample (the `if (reasons.length === 0)` return, `:284`). The WS response line fires only for failed calls or calls of at least `DEFAULT_WS_SLOW_MS = 50` ms (`src/gateway/ws-logging.ts:13`), so no RPC percentile can be computed from it. _Designed around, not removed:_ `gw.health.sample`, `worker.sample` and `rpc.minute` are the unconditional series (§4.1, §4.9, §4.2); both biases stay in the code, pinned by this optic's `verify:`.
5. **Nothing samples workers.** A tinker-bridge worker's whole life is one spawn line and one `claude exit[…] code=… signal=…` line (`extensions/tinkerclaw-tinker-bridge/src/worker.ts:797`, `:1148`): no memory, no CPU, no lifetime. A gateway restart can orphan a mid-turn worker that keeps running invisibly, and nothing records that either. _Closed in source 2026-09-25 by §9 step 5_ (`worker.spawn`, `worker.sample`, `worker.exit`, `worker.orphan`, §4.9); the item stays as the evidence the WANT answered until those rows are seen on a running gateway.
6. **Five persistent structured stores already exist and disagree on where they live** (§2b): two resolve their path from the state directory, three hardcode `$HOME/.openclaw`.

### 2c. Seams the writer builds on

- **The diagnostic event bus**, `src/infra/diagnostic-events.ts` (`emitDiagnosticEvent` `:767`, `onDiagnosticEvent` `:783`, `onDiagnosticEventTypes` `:797`). It carries `diagnostic.memory.sample`, `diagnostic.liveness.warning`, `session.state`, `session.stuck`, `queue.lane.enqueue` / `dequeue` (with `waitMs`), `run.started` / `completed`, `tool.execution.*`, `exec.process.completed` and `message.delivery.*`. Four facts shape everything built on it. (1) Every listener is handed a `structuredClone` plus a deep freeze of each event dispatched to it (`:688`), so the bridge subscribes through `onDiagnosticEventTypes`, whose per-listener type filter (a `globalThis` WeakMap) is consulted BEFORE that clone: an ignored type, `log.record` above all, costs the bridge nothing. (2) Both `onDiagnosticEvent` and `onDiagnosticEventTypes` drop `log.record` (free text) and every TRUSTED event, and `run.started` / `run.completed` (`run/attempt.ts:700`, `:712`) and `tool.execution.*` (`pi-tools.before-tool-call.ts:613`-`:681`) are emitted through `emitTrustedDiagnosticEvent`, so no listener can ever see them; that is why the §4.6 rows are direct producer calls. (3) `tool.execution.*`, `exec.process.completed`, `message.delivery.*` and `log.record` ride the async queue, which silently drops past 10,000 (`MAX_ASYNC_DIAGNOSTIC_EVENTS`, `:527`, checked at `:756`). (4) With `diagnostics.enabled: false` the bus drops every event at its source (`:748`), so every bridged row is silent; the series that must not be (`gw.health.sample`, `worker.sample`) run on timers of their own.
- **The stall clock**, `src/gateway/server/event-loop-health.ts`: a 20 ms ticker with a 60 s ring and non-destructive per-consumer readers (`createReader`, `:65`, `:138`). The file's own comment (`:175-181`) explains why a new consumer reads it instead of adding a third loop monitor.
- **SQLite helpers**: `requireNodeSqlite` (`src/infra/node-sqlite.ts`) and `configureSqliteWalMaintenance` (`src/infra/sqlite-wal.ts` — WAL, autocheckpoint, periodic TRUNCATE).
- **State-dir resolution**: `resolveStateDir` (`src/config/paths.ts:60`, honours `OPENCLAW_STATE_DIR`) and the test sandbox in `resolveTaskStateDir` (`src/tasks/task-registry.paths.ts`).
- **Worker identity**: every tinker-bridge worker is a transient systemd user unit named `tinkerclaw-worker-<gatewayPid>-<t36>-<rand>` (`worker.ts:787`), started through `systemd-run --user --pipe` (`:793-794`). ## 3. Principles

Each principle is falsifiable: the observation that would show it is not honoured is named. They apply design-principles #9, #10, #12, #17, #19 and #20 to one concern and replace none of them.

**L1. An event is a name plus typed fields, never a sentence.** Names are stable, lowercase and dotted, `<domain>.<object>[.<verb>]`; the grammar is checked by this optic's `verify:`. Every field has a declared type and unit, and the unit is in the field name (`_ms`, `_bytes`), as `algorithm-metrics.ts` already requires. _Falsified by:_ a row whose meaning needs a regex to extract, or a unit that lives only in prose.

**L2. Declare before emit.** An event is in §4, with the question it answers, before any code emits it. The writer rejects a name the catalog does not declare (counted as `unknown_name`, never thrown). The reverse is reported too: a declared event with no row in its expected window is DECLARED-and-silent in observability.md's vocabulary, and `logs catalog --silent` lists it first. _Falsified by:_ a row whose name is not in the catalog, or a catalog entry whose question nobody can state.

**L3. Cheap on the hot path: drop, never block.** An emit is one bounded array push on the calling thread — no I/O, no await. Batches leave the main thread and SQLite runs in a worker thread. Under pressure the writer drops the newest record and counts it by reason, and the counts are themselves written (`logs.writer.stats`). High-rate facts — RPC calls, history polls, index refreshes — are aggregated in memory by their producer and written as one `rollup` per window. _Falsified by:_ an emit on a request path that awaits, or a `diagnostic.cpuProfile` in which the writer's main-thread share exceeds the listener cost measured in §9 step 4.

**L4. The PII boundary is enforced by the schema, not by care.** Never stored: message text, prompt snippets, tool arguments or results, stderr, free-text error messages, contact names or numbers, host paths, credentials, raw session keys. A string field is declared `enum` (a closed set) or `id` (pattern-limited, at most 64 characters); the catalog has no free-text type, so the writer drops anything else mechanically. Session keys become `session_hash` (§7.5) plus a closed `session_kind`. The public repository is one reason; the other is that J-paper figures are drawn from this database, and a store that is PII-free by construction can be aggregated and published without a sanitization pass (design-principles #17). _Falsified by:_ any stored string that is neither an enum member nor an id, or a phone number surviving the ingest test in §9 step 3.

**L5. The journal stays human; the database is the record.** Existing text lines stay byte-identical — people and scripts grep them, and a format change has already broken a consumer silently. A migrated emitter writes both. A trend question is asked of the database; a journal line is retired only after a grep of `scripts/` and the bible proves nothing reads it. _Falsified by:_ a trend answered by scraping journalctl, or a journal line reworded in the same change that adds its event.

**L6. Retention is by class, and the working window is derived.** Four classes (§7.4): `hot`, `event`, `research`, `debug`. The day counts are ceilings; the working window shrinks automatically when the measured bytes per day would exceed the size budget, and the maintenance pass records that it did (design-principles #19: a ceiling with adaptive pressure, never a cliff). `research` is never shortened and never deleted, because papers need reproducibility. _Falsified by:_ a deleted research row, or the database over budget with no `shortened` record.

**L7. A measurement carries its provenance and its parts.** A number that will be compared with a limit carries its provenance and is stored as parts, never as a ratio (design-principles #20). `algo.outcome` keeps `algorithm-metrics.ts` rules 1–3 unchanged. _Falsified by:_ a stored ratio or percentage column.

**L8. One correlation id.** `run_id` is a column, filled wherever the producer has one (design-principles #10). Joins to the LLM ledger, the anatomy database and the task registry go through `run_id` first and `session_hash` second. _Falsified by:_ a turn-scoped event written without the `run_id` its producer held.

**L9. The recorder is watched.** The writer declares an instrument and notes it on every flush, and writes `logs.writer.stats`. A recorder that writes nothing is otherwise indistinguishable from an idle one — observability.md §1 is the whole argument. _Falsified by:_ a day of gateway activity with zero flushes that nothing reported.

**L10. Samples are unconditional.** A periodic sample fires whether or not the system is busy, at a slower cadence when idle. Suppressing idle samples makes "no data" and "stable" the same reading, and idle is where a leak's baseline lives. _Falsified by:_ a gap in a `sample` series longer than its idle cadence while the gateway was up.

## 4. The event catalog

Conventions. The executable encoding is `src/infra/events/catalog.ts` (§9 step 1, landed 2026-09-24), checked against this section in both directions on every gate run by `scripts/bible/logging-catalog.mjs` (this optic's `verify:`).

- **Kinds.** `sample` a periodic gauge · `span` carries `dur_ms` · `transition` a state change (`label` is the new state, `fields.from` the old) · `outcome` the result of one attempt · `rollup` a producer-side aggregate, stamped at the START of its window · `mark` a point occurrence.
- **Columns.** Every row has `ts_ms`, `name`, `kind`, `boot_id`, and, where the producer has them, `session_hash`, `session_kind`, `run_id`, `worker_id`. Per event: `label` (the one categorical dimension named in the row), `dur_ms`, `n1`…`n4` (hot numeric metrics whose meaning the row fixes), and `fields` (JSON with the keys the row declares).
- **Emitter.** The module (and function or `file:line`) that writes the row. "bus" means mapped from the diagnostic bus by the bridge (`bridge-diagnostic-bus.ts`, §7.5); "DIRECT" means the producer calls a shape helper itself, because the bus cannot carry the row faithfully (§4.6). A cell beginning NOT WIRED names a declared row with no producer yet and the site it belongs at; this optic's `verify:` derives that split from the code in both directions, so the marker cannot go stale either way. Line numbers were re-read at `5dea8d5fc15` (2026-09-25) and will drift; the producer strings the `verify:` gates pin are the anchor that does not.
- **Cadence.** For a `rollup` the window; for a `sample` the active and idle periods.
- **Fields follow `catalog.ts`.** Where wave 0924 changed a declaration (`compaction.run`, `worker.sample`, `instrument.transition`), the cell here moved in the same change; `logging-catalog.mjs` compares names, kinds and retention, so the rest is kept equal by review and by the tests that pin each producer's shape.

**Where each number comes from, and the traps.**

- **tinker-bridge workers: the unit's cgroup, never `/proc/<pid>`.** The child the gateway holds is `systemd-run --pipe` (`worker.ts:793-794`), so `proc.pid` is the wrapper, not `claude`; its `/proc` entry would chart the wrong process with total confidence. The unit's cgroup holds the real process tree: `memory.current` gives n1, `memory.peak` n4, `cpu.stat` `usage_usec` n2, `pids.current` the pids field. The cgroup path is resolved once per worker by asking systemd (`systemctl --user show -p ControlGroup --value <unit>`, off the hot path, 2 s after the spawn, at most three attempts because a just-spawned unit may not exist yet) and is never guessed from the gateway's own cgroup. When it cannot be resolved the sample says `source=unavailable` and carries no numbers — an honest gap, not a zero.
- **The gateway** is `worker_type=gateway`: `process.memoryUsage()` RSS for n1, the `process.cpuUsage()` delta for n2, `maxRSS` for n4 and the main isolate's heap in the heap fields — the same series shape as every other worker, so one query trends them all.
- **The FTS thread shares the process RSS; only its heap is its own.** RSS cannot be attributed to a thread, so the thread's rows say `source=isolate`: the worker answers a `stats` message with `v8.getHeapStatistics()` from its own isolate. Charting process RSS under the thread's name would count the gateway twice.
- **The events writer thread** (`worker_type=events_writer`, since `9b1a0fdf8d0`) shares the gateway's RSS exactly as the FTS thread does, so its row carries its committed heap plus external memory, `source=isolate`, never RSS. The reading rides the writer's existing `stats` request, because v8 reports only the CALLING isolate. Its id, `events-writer-<pid>-<spawn>`, changes on every respawn: a respawned thread IS a new worker, with a fresh baseline, peak and age. `emit.ts` owns that id (only it sees the spawn); a probe that times out is a `source=unavailable` row, and no thread is no row.
- **whatsmeow** (the WhatsApp transport binary, topology.md) is a direct child process, so `/proc/<pid>` is correct for it, but it is found BY PROCESS NAME, not by a handle. The Go binary is spawned inside the third-party `@whatsmeow-node/whatsmeow-node` package (its `GoProcess`), reached from `extensions/tinkerclaw-whatsapp/src/session-wm.ts`; the package keeps the handle private, so the sampler looks among this process's children for `whatsmeow-node` (the kernel's 15-character process name), or the basename of `OPENCLAW_WHATSMEOW_BINARY`. It gets no spawn or exit rows: the package owns that lifecycle.
- **Why 30 s.** The series must separate three phenomena: a leak (MB per hour, visible over hours to days), a per-turn spike (tens of seconds to minutes) and a death (an instant). 30 s resolves a turn-scale spike with several points and equals the heartbeat period, but the sampler runs on a timer OF ITS OWN: the heartbeat runs only when diagnostics are enabled, and a trend series a config flag can stop breaks L10. It costs up to 2,880 rows per worker per day. **Idle workers are written every 300 s.** Every worker is still READ every 30 s, but its row is WRITTEN only when it moved since its last row (memory by more than 1 %, or CPU above 0.1 % of one core, `WORKER_IDLE_CPU_SHARE`, because a strict zero never happens for a live process) and otherwise at the 300 s floor: a worker that wakes shows on the next tick, and an idle fleet writes a tenth of the rows. A spawned worker's first reading comes 2 s after its spawn (`WORKER_FIRST_SAMPLE_DELAY_MS`), so a worker that lives less than one tick still has a size. Spawn and exit rows, plus `memory.peak` at every sample, mean a lifetime peak is never missed between samples.
- **Why not reuse `diagnostic.memory.sample`.** It is suppressed while idle (`shouldRecordMemorySample`, `diagnostic.ts:760-766`), which L10 forbids for a trend series. It keeps firing for its current consumers.
- **A bridge worker still alive when the gateway stops gets NO exit row** (a known gap, deliberate). The gateway stops observing it, but it has not exited: it may yet be killed by the closed pipe or run on as an orphan, and an exit row stamped at shutdown would be a fabricated fact. A survivor is written as `worker.orphan` by the next gateway's first scan. The registry lives on `globalThis` (the instrument-liveness precedent), so a second copy of the module still reaches the one registry the gateway's sampler reads.

## 5. The LLM ledger — linked, never copied

The ledger (observability.md §10, `src/forensic/llm-ledger.ts`) is the record of every model call, with bodies and the human driver. This database holds no model-call rows: usage, cost, model and driver are asked of the ledger. The link is `run_id` first (the ledger's `run_id` column) and `session_hash` second — the CLI registers a `session_hash()` SQL function with the same salt, so a ledger `session_key` can be hashed at query time. Copying `usage` here would be a second derivation of a counted fact, with its own drift (design-principles #18), and would mix a never-delete private store with a rotating shareable one. **Not built yet** (§9 step 10): no `session_hash()` SQL function is registered and `logs sql` refuses `ATTACH` (§8.2), so today the join to the ledger is by `run_id`, outside the events CLI.

## 7. Storage

### 7.1 One database file of its own

`<state>/logs/events.sqlite`, where `<state>` is `resolveStateDir()`. Override with `OPENCLAW_EVENTS_DB_PATH`; turn off with `OPENCLAW_EVENTS_DB=0`. Never a hardcoded host path: the anatomy database (`context-anatomy-db.ts:30-33`), the algorithm ledger (`algorithm-metrics.ts:159`) and the ENGRAM collector (its default in `metrics.ts:49`, and its one caller's `$HOME/.openclaw/engram` in `compaction-engram.ts:151`) each hardcode `$HOME/.openclaw`; this file follows the ledger and the task registry instead. Under a test runner the production path is refused outright (the `resolveLedgerPath` precedent, `algorithm-metrics.ts:151`; `src/infra/events/paths.ts` refuses it through `isVitestRuntimeEnv`): tests are sandboxed by construction (design-principles #20).

A separate file rather than a table in a database that already exists:

| Candidate                         | Rejected because                                                                                                                                                                                           |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a table in `llm-ledger.sqlite`    | the ledger never deletes and holds private bodies; the events database rotates and must be shareable. One file cannot hold both retention policies or both privacy classes.                                |
| a table in `anatomy-timeline.db`  | UI pollers hold read snapshots that starve PASSIVE checkpoints (the 36 MB WAL); a writer sharing that file inherits the contention; its path is hardcoded.                                                 |
| JSONL files                       | no index, no retention except by whole file, every question a full scan — the shape of the stores this replaces.                                                                                           |
| scraping the journal into a table | a regex over a log line is not an interface (observability.md §7), and the lines carry what L4 forbids.                                                                                                    |
| OTEL or Prometheus export only    | the `diagnostics-otel` and `diagnostics-prometheus` extensions stay available on the same bus, but an external collector is not bounded by the state directory (FOUNDATION #9) and gives the owner no SQL. |

Joins across files were to use `ATTACH DATABASE` at query time in the CLI. As built (§8.2), `ATTACH` is REFUSED by the read-only guard: on a read-only connection it still opens any other SQLite file on the host, and the LLM ledger holds private bodies. A cross-file join needs an allow-listed attach that is still owed, and it never happens inside the writer.

### 7.2 Driver

`node:sqlite` through `requireNodeSqlite`, with `configureSqliteWalMaintenance`. It is in core, so there is no native addon to build on another machine (FOUNDATION #9); the WAL helper is typed against it; the ledger and the task registry already use it. `better-sqlite3` is declared and serves the anatomy database, but a second driver for a new store would be a second answer to one question. Both drivers are synchronous, which only matters on the main thread — and this writer does not run there.

### 7.3 Schema, version 1

`src/infra/events/schema.ts` owns every statement below (§9 step 2, landed 2026-09-24): the pragmas are `openEventsDatabase`'s, in this order, and the rest is migration 1 of `EVENTS_MIGRATIONS` (`EVENTS_SCHEMA_V1_SQL`), verbatim apart from comments — `schema.test.ts` fails if the two part.

PRAGMA auto_vacuum = INCREMENTAL;  -- before journal_mode = WAL, not merely before the first CREATE TABLE
PRAGMA journal_mode = WAL;         -- and the periodic TRUNCATE checkpoint: configureSqliteWalMaintenance
PRAGMA synchronous = NORMAL;       -- WAL-safe: a power cut may lose the last batch, never corrupt

CREATE TABLE meta (

**The pragma order is load-bearing.** `auto_vacuum` can change only while the file is empty, and the WAL switch writes page 1, so a WAL switch first freezes the file at NONE and every later `PRAGMA incremental_vacuum` (§7.4) silently reclaims nothing (measured on SQLite 3.51.3, 2026-09-24). `openEventsDatabase` sets it before the switch; `migrateEventsSchema` repairs an empty file some other caller opened the other way round (`PRAGMA auto_vacuum = INCREMENTAL` then `VACUUM`, instant on an empty file). `schema.test.ts` pins both, beside a control that shows the trap is real on the running build.

**Migrations.** `EVENTS_MIGRATIONS` is a forward-only ladder numbered 1..N — a gap or a reorder is refused at open — and `meta.schema_version` records the rung the file stands on. A shipped rung is never edited, because a file at version N has already run it; a change of shape is a new rung. The pending rungs, the `catalog` mirror and the views run in ONE `BEGIN IMMEDIATE` transaction that re-reads the version under the write lock, so two processes opening a new file at once (the writer thread and a script emitter, §7.5) migrate it once, and a rung that throws leaves the file as it was. Plain `CREATE TABLE`, not `IF NOT EXISTS`: rung 1 runs only on a version-0 file, and a version-0 file that already holds an `events` table is not ours — adopting its shape silently would be worse than failing the open. A file NEWER than the build (after a rollback deploy) is refused and left untouched, never downgraded. All DDL lives inside a rung, never in an unconditional boot `exec` (failures.md M12). Reopening a current file writes nothing and takes no write lock.

Why generic `n1`…`n4` rather than a typed column per metric: the table's shape never changes when an event is added, so there are no migrations for new events, and the typed interface is a VIEW per catalog row, generated by `schema.ts` from `catalog.ts`. A view cannot disagree with the catalog because it is derived from it: the views and the `catalog` mirror are rebuilt together, in the migration transaction, after any rung runs and whenever `meta.catalog_fingerprint` (a hash of both) differs from the running build's. A row dropped from the catalog loses its view and its `catalog` row; its events stay in `events`. The generator owns exactly the views named after catalog rows; a view a rung creates under any other name is left alone.

**View shape.** `worker.sample` → `v_worker_sample`. Every view leads with `id, ts_ms, boot_id, session_hash, session_kind, run_id, worker_id`, then the label, `dur_ms` when the row gives it a meaning, each used `n` slot, and one column per declared `fields` key; an unused slot has no column. `dur_ms` keeps its name — its meanings are prose (`hold`, `save`) and the unit belongs in the name (L1). A meaning names its column by one rule (`viewColumnName`): a parenthetical lists a label's values, not its name (`outcome (hit, miss)` → `outcome`); a snake_case identifier followed by prose names itself and keeps its unit (`cpu_ms since the last sample` → `cpu_ms`); any other phrase becomes one snake_case name (`tool name` → `tool_name`, `hook:plugin` → `hook_plugin`, `algorithm/variant` → `algorithm_variant`). Aliases are quoted because some meanings and field keys are SQL keywords (`drop`, `from`, and since §9 step 4 `to`, the destination verdict of `instrument.transition`). A derived name that would collide with a base column, another slot or a field key falls back to the raw slot (`label`, `n2`) so a view always builds; `schema.test.ts` fails if any real catalog row needs that fallback, so a colliding meaning is renamed in §4 rather than shipped. The view for `worker.sample`, exactly as generated (the same test fails if this block and the generator disagree):

```sql
CREATE VIEW "v_worker_sample" AS
SELECT id,
       ts_ms,
       boot_id,
       session_hash,
       session_kind,
       run_id,
       worker_id,
       label AS "worker_type",
       n1 AS "mem_bytes",
       n2 AS "cpu_ms",
       n3 AS "age_ms",
       n4 AS "peak_bytes",
       json_extract(fields, '$.source') AS "source",
       json_extract(fields, '$.pids') AS "pids",
       json_extract(fields, '$.heap_used_bytes') AS "heap_used_bytes",
       json_extract(fields, '$.heap_limit_bytes') AS "heap_limit_bytes"

WHERE name = 'worker.sample';
```

### 7.4 Retention, rotation, vacuum and the size budget

| Class      | Raw window (ceiling) | After the window                          | Holds                                                   |
| ---------- | -------------------- | ----------------------------------------- | ------------------------------------------------------- |
| `hot`      | 14 days              | rolled up into `rollup_1h`, kept 400 days | samples, spans, rollups                                 |
| `event`    | 180 days             | deleted                                   | transitions, outcomes, marks                            |
| `research` | never deleted        | —                                         | `algo.outcome`, `engram.metric`, every `j.*`            |
| `debug`    | 48 hours             | deleted                                   | reserved for opt-in verbose families; none declared yet |

**The maintenance pass** runs daily in the writer thread. It rolls up the hours leaving the hot window (idempotent: `INSERT OR REPLACE` on the rollup key), deletes in batches sized so one transaction stays near 50 ms (derived from the previous pass's measured delete rate; the first pass uses 5,000 rows), runs `PRAGMA incremental_vacuum`, then a TRUNCATE checkpoint, and records `logs.retention.run`. A long single delete would hold the write lock and back up the queue — hence batches.

**The size budget.** Ceiling `OPENCLAW_EVENTS_DB_MAX_BYTES`, default 512 MiB. Estimated volume (provenance: estimated; replace with `logs.writer.stats` after the first week):

| Source                                                                                 | Rows per day     | Basis                                            |
| -------------------------------------------------------------------------------------- | ---------------- | ------------------------------------------------ |
| `gw.health.sample`                                                                     | 2,880            | every 30 s                                       |
| `worker.sample`                                                                        | 3,000 to 30,000  | 30 s active, 300 s idle, one to ten live workers |
| `rpc.minute`                                                                           | 15,000 to 30,000 | ten to twenty methods active per minute          |
| `history.minute`, `transcript.index.minute`, `fts.request.minute`, `instrument.census` | about 8,000      | 60 s windows, a few labels each                  |
| `store.lock.held`, `store.save`                                                        | 5,000 to 20,000  | per acquisition                                  |
| `turn.span`, `hook.span`, `tool.done`                                                  | about 5,000      | about 200 turns with about 25 rows each          |
| everything else                                                                        | under 2,000      | transitions and marks                            |

That is 40,000 to 100,000 rows a day at roughly 150 bytes with indexes — 6 to 15 MB a day, so the 14-day hot window holds 85 to 210 MB. `event` and `research` rows are a small fraction. The ceiling leaves two to five times headroom.

**The derived window.** At each pass, `hot_days = min(14, floor((budget − research_bytes − event_bytes) / hot_bytes_per_day))`, then the same for `event` against what remains; `research` is never cut. When a window shrinks, `logs.retention.run` records `shortened=true` and the journal says why.

### 7.5 The writer

- **The API.** `emitEvent(name, record)` is synchronous and O(1): a `Map` lookup of the catalog entry (unknown names are counted and dropped), removal of undeclared keys (counted in `undeclaredKeys`) and of values outside their declared type (counted in `invalidValues`), conversion of a session key into `session_hash` and `session_kind`, and a push onto a bounded array. It never throws, never awaits and never touches the disk or the database. **What the value rules check, exactly.** A number must be finite; an `enum` or `id` value must be id-shaped (at most 64 characters, never starting with `+`); a label must be printable ASCII without whitespace, at most 128 characters. Closed-set MEMBERSHIP is not checked here; only the `logs.ingest` door enforces the sets (§8.2), because an in-process producer cannot drift far from `catalog.ts` without a review noticing, while a browser tab can.
- **The L4 refusal of session-key-shaped values** (since `3700115a16d`). The id and label patterns both accept `agent:<id>:<rest>`, so a producer passing a RAW session key into `label`, `run_id`, `worker_id` or a string field would have stored it verbatim. The writer refuses the WHOLE record when any of those parses as a session key through the canonical parser (`parseAgentSessionKey`, the same call `query.ts` redacts with: one owner for what a session key is, never a second regex), counted under `session_key_in_column`. A length check and one anchored prefix test run first, so emit stays O(1). The whole record goes, not the slot, because a blanked `worker.sample` would chart a row with no worker type. A key nested inside a `json` object is deliberately not walked (that is not O(1)); read-side redaction is the backstop there (§8.2).
- **The session hash.** HMAC-SHA256 keyed with a 32-byte random salt at `<state>/logs/events.salt` (mode 0600, created on first use, never stored in the database), truncated to 16 hex characters. An unkeyed hash of a key that embeds a phone number can be reversed by enumeration; a keyed one cannot. `session_kind` is derived through the canonical session-key parser family (architecture.md, Session identity row) into a closed set — main, tinker, whatsapp, cron, subagent, other — never through a new regex (design-principles #18). The cost: losing the salt breaks joins to the ledger's raw keys, never the database itself.
- **One writer per process, on a `globalThis` slot.** The process-wide writer, its pre-start drop counter and the boot id of every writer this process started live on `Symbol.for("openclaw.eventsWriter.state")` (the agent-events precedent). An extension reaches `emitEvent` through `openclaw/plugin-sdk/fork-telemetry`, which dist may bundle as a separate copy of `emit.ts`; with a module-level variable that copy would hold a writer that never started and drop every row it was handed as `not_started`. Emits before `startEventWriter` are counted as `not_started` and carried into the live writer's counters.
- **The queue.** Bounded at 20,000 records, a few MB. On overflow the newest record is dropped and `dropped_by_reason.queue_full` increments: a burst loses its tail, never the history already queued.
- **The flush.** Every second, or at 500 queued records, on an unref'd timer; one batch in flight at a time, the next waiting for the acknowledgement. Backpressure lands in the bounded queue, never on the caller. At most 5,000 records leave per `postMessage` (`EVENTS_INSERT_BATCH_MAX`): a structured clone of the whole queue would stall the loop.
- **The thread.** One `worker_threads` Worker owns the connection, the prepared INSERT (one transaction per batch), the maintenance pass and the WAL checkpoint. Its lifecycle copies the FTS worker's: unref'd when idle, an old-generation cap, a respawn backoff after a crash. **There is no in-thread fallback**: writing SQLite on the main thread is the cost this design exists to avoid, so while the worker is down records queue up to the bound and are then dropped with a counter. Its old-generation cap is 512 MB (roomy, because the TypeScript source path loads tsx into the worker), its respawn backoff 60 s, and a 600 s request timeout exists to detect a DEAD worker, never as backpressure. Since §9 step 10 the thread also holds a SECOND, read-only connection, opened by `query.ts` on the first saved query, so `writer-worker.ts` itself still opens nothing but `openEventsDatabase`.
- **The requests on the wire.** Besides insert batches the worker answers, serially: `stats` (counters, db and WAL bytes, and the thread's OWN isolate, since v8 reports only the calling isolate; the worker sampler charts it as `worker_type=events_writer`, §4.9); `maintenance` (§7.4); `ledger`, the compaction ledger's restart seed (§4.7), sent as session HASHES and leaving out this process's boot ids, soft-timed at 30 s; and `query`, a SAVED query by NAME with its bound parameters (§8.2), whose main-thread wait is soft at budget plus 10 s. No SQL text crosses the wire. Every read is soft-timed: a timeout fails only that request, because a request queued behind a maintenance pass is late, not proof of a dead worker, so inspection can never tear the writer down.
- **The bus bridge.** One listener in `bridge-diagnostic-bus.ts`, subscribed through `onDiagnosticEventTypes` to the allow-list `BRIDGED_BUS_TYPES`: `diagnostic.liveness.warning`, `diagnostic.memory.pressure`, `session.stuck`, `queue.lane.dequeue` and `session.state`, the rows marked "bus" in §4. The filter runs BEFORE the per-listener clone, so every other type costs nothing, `log.record` above all; trusted events never arrive, which is why the §4.6 rows are DIRECT. Measured 2026-09-25, synthetic (node v22.23.1, 3 runs of 20,000 emits, p50): an unfiltered no-op listener raises every event from about 0.6-0.9 µs to 3.9-4.5 µs; with the filter, ignored types stay at about 0.6-0.7 µs and a bridged event costs about 4.0-4.6 µs (`bridge-diagnostic-bus.test.ts` reruns the arms). The live `diagnostic.cpuProfile` before and after is owed on a running gateway (§9 step 4). The same start installs the instrument-liveness report sink (§4.10), which keeps writing with the bus off. Started after `startEventWriter`: with no writer it installs nothing.
- **Shutdown.** Flush with a 2 s deadline, then terminate; records still queued are counted in the final journal line. The gateway's close prelude stops the bridge, the health sampler and the worker sampler first, so the final flush carries their last rows.
- **Self-watch.** The writer declares instrument `logs:writer-flush` lazily at its first flush (observability.md rule 5), notes it on every batch, and writes `logs.writer.stats` every 60 s.
- **Script emitters** (`scripts/test-invariants.mjs`, the ORCA lease hook) are short-lived processes: they would open the same file through the same schema module, write one small transaction at exit, and rely on WAL and `busy_timeout`, with no IPC to the gateway. NOT BUILT: both of their rows (`j.bible.invariants`, `j.orca.lease`) are NOT WIRED. The one script that writes today, `scripts/events-backfill.ts`, goes through the real writer core (§4.11).
- **UI emitters** go through `logs.ingest` (§8.2) from `tinker-ui/src/event-ingest.ts`: a buffer bounded at 200 events (newest dropped past it), at most 40 per call and one call in flight, every 5 s while it holds rows, backing off to 60 s on failure, each call with its own 10 s timeout (`UI_EVENTS_RPC_TIMEOUT_MS`, set by the sender `tinker-ui/src/app.ts` hands the client), and every loss counted by cause. Every string it sends is a member of a closed set or a UUID run id. The UI never opens the file.

## 8. Querying

### 8.1 Worked queries

All are plain SQLite. Where order matters, `id` breaks ties (design-principles #20). Beyond the 14-day hot window the same shapes read `rollup_1h` (`n1_avg`, `n4_max`, `dur_p99`). Each query below is saved (§8.2) under the name in its heading and parameterized by `since` (and `label` where it filters one); the text here is the human-readable form. The J10 query is the exception.

**Worker memory per worker type per day** (saved as `worker-memory-daily`):

```sql
SELECT date(ts_ms / 1000, 'unixepoch', 'localtime') AS day,
       label AS worker_type,
       count(DISTINCT worker_id) AS workers,
       round(avg(n1) / 1048576.0, 1) AS avg_mem_mib,
       round(max(n4) / 1048576.0, 1) AS peak_mem_mib
FROM events
WHERE name = 'worker.sample'
  AND ts_ms >= strftime('%s', 'now', '-30 days') * 1000
GROUP BY day, worker_type
ORDER BY day, worker_type;
```

**Does a worker grow over its own lifetime?** (saved as `worker-growth`) A least-squares slope per worker, in MiB per hour, for workers alive at least an hour:

```sql
WITH s AS (
  SELECT worker_id, label AS worker_type,
         (ts_ms - min(ts_ms) OVER (PARTITION BY worker_id)) / 3600000.0 AS x,
         n1 / 1048576.0 AS y
  FROM events
  WHERE name = 'worker.sample' AND n1 IS NOT NULL
)
SELECT worker_id, worker_type, count(*) AS samples, round(max(x), 1) AS hours,
       round((count(*) * sum(x * y) - sum(x) * sum(y))
             / nullif(count(*) * sum(x * x) - sum(x) * sum(x), 0), 2) AS mib_per_hour
FROM s
GROUP BY worker_id, worker_type
HAVING max(x) >= 1
ORDER BY mib_per_hour DESC
LIMIT 20;
```

**Session-store lock hold p99 per day** (saved as `lock-hold-p99`; nearest-rank; add `label` to the partition for per-site figures):

```sql
WITH h AS (
  SELECT date(ts_ms / 1000, 'unixepoch', 'localtime') AS day, dur_ms,
         row_number() OVER (PARTITION BY date(ts_ms / 1000, 'unixepoch', 'localtime')
                            ORDER BY dur_ms, id) AS rn,
         count(*) OVER (PARTITION BY date(ts_ms / 1000, 'unixepoch', 'localtime')) AS n
  FROM events
  WHERE name = 'store.lock.held'
)
SELECT day, max(n) AS holds,
       min(CASE WHEN rn >= 0.99 * n THEN dur_ms END) AS p99_hold_ms,
       max(dur_ms) AS max_hold_ms
FROM h
GROUP BY day
ORDER BY day;
```

**Event-loop stalls against RPC load** (saved as `loop-stalls-vs-rpc`). 1,000 ms is the existing liveness bar (`DEFAULT_LIVENESS_EVENT_LOOP_DELAY_WARN_MS`, `diagnostic.ts:53`), kept so this reading and the journal's warning agree:

```sql
WITH loop AS (
  SELECT ts_ms / 60000 AS minute, max(n2) AS loop_max_ms
  FROM events WHERE name = 'gw.health.sample'
  GROUP BY minute
),
rpc AS (
  SELECT ts_ms / 60000 AS minute, sum(n1) AS calls, sum(n2) AS handler_ms
  FROM events WHERE name = 'rpc.minute'
  GROUP BY minute
)
SELECT CASE WHEN loop.loop_max_ms >= 1000 THEN 'stalled' ELSE 'ok' END AS loop_state,
       count(*) AS minutes,
       round(avg(coalesce(rpc.calls, 0)), 1) AS avg_calls_per_min,
       round(avg(coalesce(rpc.handler_ms, 0)), 0) AS avg_handler_ms_per_min
FROM loop LEFT JOIN rpc USING (minute)
WHERE loop.minute >= strftime('%s', 'now', '-7 days') / 60
GROUP BY loop_state;
```

**Which methods dominate the stalled minutes** (saved as `stalled-minute-methods`):

```sql
WITH stalled AS (
  SELECT DISTINCT ts_ms / 60000 AS minute
  FROM events
  WHERE name = 'gw.health.sample' AND n2 >= 1000
)
SELECT e.label AS method, sum(e.n1) AS calls, sum(e.n2) AS handler_ms, max(e.n3) AS worst_ms
FROM events e JOIN stalled s ON e.ts_ms / 60000 = s.minute
WHERE e.name = 'rpc.minute'
GROUP BY method
ORDER BY handler_ms DESC
LIMIT 10;
```

**J-coverage — which paper metrics are silent** (saved as `j-coverage`; observability.md's DECLARED-and-silent, per paper):

```sql
SELECT c.paper, c.name, count(e.id) AS rows_7d,
       datetime(max(e.ts_ms) / 1000, 'unixepoch', 'localtime') AS last_seen
FROM catalog c
LEFT JOIN events e
  ON e.name = c.name AND e.ts_ms >= strftime('%s', 'now', '-7 days') * 1000
WHERE c.paper IS NOT NULL
GROUP BY c.paper, c.name
ORDER BY rows_7d, c.paper, c.name;
```

**J12 — prompt-cache parts per week** (saved as `j12-prompt-cache`; the share is derived by the reader as `cache_read / (cache_read + uncached_input + cache_write)`, never stored):

```sql
SELECT strftime('%Y-W%W', ts_ms / 1000, 'unixepoch') AS week,
       json_extract(fields, '$.model') AS model,
       sum(json_extract(fields, '$.metrics.cacheReadTokens')) AS cache_read,
       sum(json_extract(fields, '$.metrics.inputTokens')) AS uncached_input,
       sum(json_extract(fields, '$.metrics.cacheWriteTokens')) AS cache_write
FROM events
WHERE name = 'algo.outcome' AND label LIKE 'prompt-cache/%'
  AND json_extract(fields, '$.provenance.cacheReadTokens') = 'per-call-measured'
GROUP BY week, model
ORDER BY week, model;
```

**J1 — compaction by variant** (saved as `j1-compaction-by-variant`):

SELECT label AS variant, json_extract(fields, '$.outcome') AS outcome, count(*) AS n,

### 8.2 CLI and RPC

As built in §9 step 10 (`4c86c2b1f17`, `387cdbd2e61`, `9d6b5a12e50`).

**The saved-query registry** (`src/infra/events/saved-queries.ts`) is the ONE place a named question lives as SQL. Twelve entries: §8.1's `worker-memory-daily`, `worker-growth`, `lock-hold-p99`, `loop-stalls-vs-rpc`, `stalled-minute-methods`, `j-coverage`, `j12-prompt-cache` and `j1-compaction-by-variant`; `history-resets-by-reason` and `outbox-proof-latency`; `worker-memory-trend`, the owner's per-worker slope over a fixed 7 days (MiB per hour through `v_worker_sample`; a leak is a slope that stays positive day after day), owned here and re-exported by `samplers/worker-resources.ts` so the sampler's real-database test runs the same text; and `catalog`. Every entry is one SELECT or WITH, takes only the named parameters it declares (`@since_ms` for `since`, `@label` for `label`), reads only `events`, `catalog`, `rollup_1h` or a generated `v_*` view, and selects no session column; `query.test.ts` runs every entry against a seeded database.

**CLI** — subcommands of the existing `logs` command (`src/cli/logs-cli.ts:615`); a bare `tinkerclaw logs` stays the file-log tail it is today.

- `tinkerclaw logs query [name] [--since <duration>] [--label …] [--limit n] [--json]` asks the gateway's `logs.query` by NAME; with no name, or `--list`, it prints the registry without a call; `--local [--db <path>]` runs the same entry against the file in the isolated runner below, with the same validation and output guard.
- `tinkerclaw logs sql "<SELECT …>" [--limit n] [--budget-ms n] [--db <path>]` is LOCAL ONLY, never over RPC. The statement must pass `assertReadOnlySelect` before any file is looked for, then runs in a CHILD PROCESS on a read-only connection. The `--attach ledger,anatomy,tasks` this section once promised is NOT built: `ATTACH` is refused, because on a read-only connection it still opens any other SQLite file on the host, and the LLM ledger holds private bodies. An allow-listed attach is owed if it is wanted.
- `tinkerclaw logs catalog [--silent] [--since <duration>] [--local]` prints the catalog with row counts in the window and last-seen times; `--silent` lists declared-but-silent events first.

**RPC** — under the existing `logs.*` namespace, each method classified in `src/gateway/method-scopes.ts` and listed in `server-methods-list.ts` in the change that added it (an unclassified method is default-deny for clients and silently ADMIN on the server, observability.md §6 #11).

- `logs.query({name, params?: {since?, label?}, limit?})` — READ. The main thread only validates (`resolveSavedQuery`: an unknown name or key, or SQL text as a name, is INVALID_REQUEST before any database work) and posts the NAME to the writer thread, which runs the entry on its read-only connection: at most 5,000 rows (default 1,000), a 5 s budget. No writer, a stopping writer or a query error answers UNAVAILABLE with the reason. There is no raw SQL over RPC: a long ad-hoc query holds a read snapshot that blocks WAL checkpoints (the anatomy WAL lesson), and SQL text from a client is an injection surface.
- `logs.catalog({silent?, since?})` — READ. The `catalog` saved query; `silent: true` puts the declared events with no row in the window first (L2's DECLARED-and-silent).
- `logs.writer.stats` — READ (§9 step 3). The writer's counters, including its thread's own isolate.
- `logs.ingest({events})` — WRITE, never READ: READ is also granted to WRITE holders, so a READ classification would hand every read-only token a write path into the store. The gate (`src/infra/events/ingest.ts`) is the one door where the catalog is ENFORCED rather than trusted: only names the catalog marks `uiIngestable` (the UI cannot forge a gateway event); exactly the row's shape (declared keys, slots only where the row gives them a meaning, declared `fields` keys); and every value a finite number, a boolean, a member of its CLOSED set or a short id without `+` or `/`. `json` fields are refused from this door outright. A record that breaks any rule is refused WHOLE and recorded as a `logs.ingest.rejected` row. Batches are capped at 100 records (`oversize`); each client gets 600 rows per 60 s, then ONE `rate_limited` row per window and silence, so no client can make the door write more than budget plus one rows per window. A refused record is not an RPC failure: a well-formed call answers ok with counts.

**Read-only by construction, in three layers** (`query.test.ts` holds each on its own):

1. the connection is opened `readOnly: true` with `PRAGMA query_only`, so INSERT, UPDATE, DELETE and CREATE (TEMP included) fail, and an attached file would inherit the read-only open;
2. `assertReadOnlySelect` admits exactly ONE statement whose first keyword is SELECT or WITH (and a WITH whose main statement is a SELECT). This layer is not redundant: on a read-only connection `VACUUM INTO '<file>'` still writes a new file, `ATTACH` still opens any other SQLite file on the host, and `node:sqlite`'s `prepare()` silently DROPS everything after the first statement instead of refusing it;
3. there is no path from a client to SQL text at all: the RPC takes a registry NAME.

**Budgets: soft between rows, hard only in a child process.** `node:sqlite` on node 22 has no progress handler or interrupt, and a `worker_threads` `terminate()` does NOT stop a running `sqlite3_step` (measured 2026-09-25 on node 22.23: a 13 s aggregate ran to the end after a terminate at 0.3 s, and `process.exit()` waited for it). So every runner stops BETWEEN ROWS at its budget (`truncated: "time_budget"`) and at its row cap (`truncated: "row_cap"`); the isolated ad-hoc runner is also SIGKILLed at budget plus 1.5 s, the only hard wall, which is why ad-hoc SQL runs in a child process and nowhere else; and a saved query in the writer thread has no hard wall, because its entries are fixed, windowed reads of `events_name_ts` and the main thread's wait is soft, so a slow one fails its RPC without tearing the writer down. `logs sql` returns at most 50,000 rows, with a 10 s default budget and a 120 s ceiling; no `since` reaches past ten years.

**L4 on the way out.** Rows hold no raw session key because the writer hashes and refuses them (§7.5); on top of that the runner refuses a result column named like a session key, so no saved query can grow into returning one, and a cell that parses as a raw session key through the canonical parser is replaced by `<redacted:session_key>` and counted in `redactedSessionKeys`. A nonzero count is a defect report, not a normal reading.
